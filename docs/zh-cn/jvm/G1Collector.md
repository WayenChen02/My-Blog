# G1 垃圾收集器详解

## G1 概述

G1（Garbage-First）是为了解决 CMS 内存碎片导致频繁 Full GC、Parallel 系列停顿不可控的痛点而设计的区域化分代式整堆收集器。

## 核心内存布局：Region 化分代

G1 逻辑上保留新生代和老年代的分代模型，但物理上不再使用连续的内存块，而是将整个 Java 堆划分为多个大小固定、数量相等的 Region：

- **Region 大小**：1M~32M，必须是 2 的幂，JVM 启动时自动计算，也可通过 -XX:G1HeapRegionSize 手动指定

- **Region 类型**：
  - **Eden Region**：新生代伊甸区，存放新创建的对象
  - **Survivor Region**：新生代幸存者区，存放 Young GC 后存活的对象
  - **Old Region**：老年代区，存放长期存活、晋升后的对象
  - **Humongous Region**：巨型对象区，存放大小≥Region 50% 的巨型对象，不会晋升到老年代

## 核心设计思想：Garbage-First（垃圾优先）

G1 不会每次回收整个堆，而是优先回收垃圾占比最高、回收收益最大的 Region，每次只回收一部分 Region，通过控制回收的 Region 数量，将 STW 停顿时间严格控制在 -XX:MaxGCPauseMillis（默认 200ms）的目标范围内，实现可预测的停顿。

## 完整垃圾回收流程（并发标记周期）

### 1. 初始标记（Initial Mark）

**执行特性**：STW 极短停顿，多线程并行执行

**核心动作**：标记所有与 GC Roots 直接关联的对象，记录 TAMS 指针为并发标记做准备；通常依附于 Young GC 的停顿完成，无额外开销

### 2. 并发标记（Concurrent Mark）

**执行特性**：与用户线程完全并发执行，无 STW

**核心动作**：遍历整个堆的对象图，标记所有可达的存活对象；通过写屏障 + SATB 快照算法记录引用变更，避免漏标

### 3. 最终标记（Remark）

**执行特性**：STW 短停顿，多线程并行执行

**核心动作**：修正并发标记期间的对象引用变更，处理 SATB 记录的引用队列，完成存活对象的最终标记；相比 CMS 增量更新，扫描开销更小，停顿更短

### 4. 筛选回收（Cleanup / Evacuation）

**执行特性**：STW 可控停顿，多线程并行执行

**核心动作**：按回收收益对 Region 排序，根据停顿目标选择回收集合；将选中 Region 的存活对象复制到空 Region，直接清空原 Region，全程无内存碎片

## 核心底层机制

### 1. Remembered Set（RSet，记忆集）

- **定义**：每个 Region 维护一个独立的 RSet，记录其他 Region 中指向本 Region 对象的引用

- **核心价值**：回收某个 Region 时，无需扫描整个堆，只需扫描本 Region 的 RSet 即可判断对象是否被外部引用，是 G1 实现局部 Region 回收的核心基础

### 2. SATB（Snapshot-At-The-Beginning，起始快照）算法

- **核心原理**：并发标记开始时，给当前堆的对象图拍一张快照，快照中所有存活的对象，本次 GC 全部视为存活

- **核心动作**：通过写屏障拦截并发阶段「删除引用」的操作，把被删除的对象记录到 GC 队列，最终标记阶段统一扫描

- **优势**：最终标记阶段无需重新遍历完整引用链，大幅缩短 STW 停顿时间，适配 G1 的可控停顿目标

## G1 的三种 GC 类型

### 1. Young GC（新生代 GC）

**触发条件**：Eden Region 被占满

**回收范围**：所有 Eden Region + 所有 Survivor Region

**执行特性**：多线程并行执行，全程 STW，停顿时间极短

### 2. Mixed GC（混合 GC，G1 核心回收方式）

**触发条件**：老年代 Region 占堆内存的比例达到
 IHOP 阈值（默认 45%）

**回收范围**：所有新生代 Region + 部分回收收益最高的老年代 Region + 所有 Humongous Region

**核心价值**：增量回收老年代，将停顿控制在目标范围内，避免整堆回收的长停顿，是 G1 最常用的回收方式

### 3. Full GC（整堆 Full GC，必须避免的最坏情况）

**触发条件**：
- Mixed GC 回收速度跟不上对象分配速度
- 对象晋升失败
- 巨型对象无足够空间存放
- 并发模式失败

**执行特性**：
- JDK10 及以上为多线程并行执行
- JDK9 及之前为单线程 Serial Old 执行
- 全程 STW，停顿时间极长

**优化方向**：
- 调大堆内存
- 放宽最大停顿时间
- 调整 IHOP 阈值
- 减少巨型对象产生

## G1 的调优建议

1. **设置合理的最大停顿时间**：根据业务需求设置 -XX:MaxGCPauseMillis（默认 200ms）
2. **调整堆内存大小**：确保堆内存足够大，避免频繁 GC
3. **设置 IHOP 阈值**：通过 -XX:InitiatingHeapOccupancyPercent 调整老年代触发并发标记的阈值
4. **调整并行线程数**：根据 CPU 核数设置合理的并行线程数
5. **避免巨型对象**：尽量减少创建大小≥Region 50% 的对象
6. **监控 GC 日志**：关注 Mixed GC 的频率和停顿时间，及时调整配置

## G1 的适用场景

- **堆内存≥6G** 的应用
- **对延迟和吞吐量都有要求** 的中大型服务端应用
- **需要可预测停顿时间** 的应用
- **JDK9 及以上** 的默认垃圾收集器

## 总结

G1 是一种兼顾低延迟和高吞吐量的垃圾收集器，通过 Region 化分代、垃圾优先策略和可控停顿时间，解决了 CMS 的内存碎片问题和 Parallel 系列的停顿不可控问题，是目前生产环境中最常用的垃圾收集器之一。
