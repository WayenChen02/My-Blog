# CMS 垃圾收集器详解

## CMS 概述

CMS（Concurrent Mark Sweep）是基于标记 - 清除算法的并发老年代收集器，专为互联网高并发、低停顿要求的服务端应用设计。

## CMS 完整垃圾回收流程

CMS 的完整回收分为 4 个核心阶段：

### 1. 初始标记（Initial Mark）

**执行特性**：STW 短停顿，多线程并行执行

**核心动作**：仅标记 GC Roots 直接关联的对象，不遍历整个对象图，耗时极短

### 2. 并发标记（Concurrent Mark）

**执行特性**：与用户线程完全并发执行，无 STW

**核心动作**：
- 从初始标记的对象出发，遍历整个堆的对象图，标记所有可达的存活对象
- 通过写屏障 + 增量更新记录引用变更，避免漏标

### 3. 最终标记（Remark）

**执行特性**：STW 短停顿，多线程并行执行

**核心动作**：修正并发标记期间的对象引用变更，重新扫描增量更新记录的引用，完成所有存活对象的最终标记

### 4. 并发清除（Concurrent Sweep）

**执行特性**：与用户线程完全并发执行，无 STW

**核心动作**：遍历堆内存，清除所有不可达的垃圾对象，释放内存空间

## CMS 的优缺点

### 优点
- **低延迟**：核心阶段几乎不卡顿用户线程，STW 停顿时间极短
- **并发回收**：充分利用多核 CPU 资源，提高系统吞吐量
- **适合高并发场景**：专为互联网服务端应用设计

### 缺点
1. **内存碎片**：标记 - 清除算法产生大量内存碎片，老年代空间利用率下降，容易提前触发 Full GC
2. **CPU 资源占用**：并发阶段占用 CPU 资源，对 CPU 核数敏感（默认占用 1/4 的 CPU 核数），低核数服务器会严重影响用户线程吞吐量
3. **Concurrent Mode Failure 风险**：并发回收阶段，对象晋升老年代时空间不足，会立即触发 Full GC，退化为单线程 Serial Old 回收，停顿时间极长
4. **浮动垃圾**：并发阶段产生浮动垃圾，本次 GC 无法回收，只能等到下一次 GC 处理
5. **空间预留**：需要预留足够的老年代空间，避免并发回收期间对象晋升失败

## CMS 的调优建议

1. **合理设置老年代大小**：避免老年代空间过小导致频繁 CMS GC
2. **调整并发线程数**：根据 CPU 核数设置合理的并发线程数（-XX:ParallelCMSThreads）
3. **设置 CMS 启动阈值**：通过 -XX:CMSInitiatingOccupancyFraction 设置合适的老年代占用阈值，避免过早或过晚触发 CMS GC
4. **启用内存碎片整理**：通过 -XX:+UseCMSCompactAtFullCollection 和 -XX:CMSFullGCsBeforeCompaction 启用 Full GC 时的内存碎片整理
5. **预留足够空间**：确保老年代有足够的空间容纳并发回收期间的对象晋升

## CMS 的适用场景

- **对延迟敏感的服务端应用**：如 Web 服务器、API 网关等
- **多核 CPU 环境**：能充分利用多核优势进行并发回收
- **内存较大的应用**：但不宜过大，否则并发标记时间过长

## 注意事项

- CMS 已在 JDK 9 中被标记为 deprecated，在 JDK 14 中被移除
- 对于需要低延迟的应用，推荐使用 G1 或 ZGC 收集器
- 在使用 CMS 时，应密切监控 Concurrent Mode Failure 事件，及时调整配置
