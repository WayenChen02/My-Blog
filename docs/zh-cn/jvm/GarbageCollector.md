# 垃圾收集器分类与核心特性

## 垃圾收集器分类

垃圾收集器按回收范围分为三类：
- **新生代垃圾收集器**：Serial、ParNew、Parallel Scavenge
- **老年代垃圾收集器**：Serial Old、Parallel Old、CMS
- **整堆（全堆）垃圾收集器**：G1、ZGC、Shenandoah

## 1. 串行收集器组合：Serial + Serial Old

**执行特性**：单线程串行执行，垃圾回收全程 STW，只有一条 GC 线程工作，回收期间用户线程完全暂停

**算法**：
- Serial（新生代）使用 标记 - 复制算法
- Serial Old（老年代）使用 标记 - 整理算法

**优点**：
- 实现简单
- 单核 CPU / 小内存场景下，无多线程切换开销，回收效率极高
- 内存占用最低

**缺点**：
- 多核场景下无法利用 CPU 多核优势
- STW 停顿时间长
- 不适合大堆、高并发服务端应用

**适用场景**：
- 客户端应用
- 单核服务器
- 堆内存 < 4G 且 GC 频率极低的简单应用

## 2. 并行新生代收集器：ParNew、Parallel Scavenge

### ParNew

**执行特性**：多线程并行执行，是 Serial 收集器的多线程版本，回收全程 STW

**算法**：标记 - 复制算法

**核心定位**：低延迟优先，专为配合 CMS 老年代收集器设计，是唯一能与 CMS 配合的新生代收集器

**优点**：
- 多核场景下利用 CPU 多核优势
- 大幅缩短新生代 GC 的 STW 停顿时间

### Parallel Scavenge

**执行特性**：多线程并行执行，回收全程 STW

**算法**：标记 - 复制算法

**核心定位**：吞吐量优先（吞吐量 = 用户代码运行时间 /(用户代码运行时间 + GC 总时间)），主打最大化程序运行效率，而非最小化停顿

**核心特性**：
- 支持 自适应内存调节策略（-XX:+UseAdaptiveSizePolicy）
- JVM 自动调整新生代大小、Eden/Survivor 比例，无需手动调优

**配套组合**：
- JDK1.6 及以上，配套老年代收集器为 Parallel Old，形成完整的吞吐量优先组合

## 3. 并行老年代收集器：Parallel Old

**执行特性**：多线程并行执行，全程 STW

**算法**：标记 - 整理算法

**核心定位**：Parallel Scavenge 的老年代配套版本，共同组成吞吐量优先的收集器组合

**适用场景**：
- 后台数据分析
- 批处理等注重吞吐量、对停顿不敏感的应用

## 4. 并发老年代收集器：CMS（Concurrent Mark Sweep）

**执行特性**：并发为主、并行为辅，核心回收阶段与用户线程并发执行，主打极低 STW 停顿

**算法**：标记 - 清除算法

**核心定位**：低延迟优先，专为互联网高并发、低停顿要求的服务端应用设计

**优点**：
- 并发回收，核心阶段几乎不卡顿用户线程
- STW 停顿时间极短

**缺点**：
- 标记 - 清除算法产生大量内存碎片，老年代空间利用率下降，容易提前触发 Full GC
- 并发阶段占用 CPU 资源，对 CPU 核数敏感（默认占用 1/4 的 CPU 核数），低核数服务器会严重影响用户线程吞吐量
- 存在 Concurrent Mode Failure 风险：并发回收阶段，对象晋升老年代时空间不足，会立即触发 Full GC，退化为单线程 Serial Old 回收，停顿时间极长
- 并发阶段产生浮动垃圾，本次 GC 无法回收，只能等到下一次 GC 处理

## 5. 整堆收集器：G1

**执行特性**：同时支持并行与并发，核心阶段可与用户线程并发执行，STW 停顿时间可控

**核心设计目标**：在可控的停顿时间内实现高回收效率，解决 CMS 内存碎片、Parallel 系列停顿不可控的痛点

**适用场景**：
- 堆内存≥6G
- 对延迟和吞吐量都有要求的中大型服务端应用
- JDK9 及以上默认垃圾收集器

## 6. 整堆收集器：ZGC

**执行特性**：全并发回收，几乎所有阶段都与用户线程并发执行，最大 STW 停顿不超过 1ms

**核心定位**：超低延迟优先，面向大堆 / 超大堆（TB 级）内存场景

**引入版本**：
- JDK11 引入
- JDK17 正式 GA
